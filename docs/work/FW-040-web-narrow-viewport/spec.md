# Web 窄屏适配

> ID：`FW-040`
>
> 状态：`approved`

## 目标

Web 控制台在 768 到 1280 宽度下，侧栏仍占 240px，内容区只剩约 500px，六个宽表格要横向滚大半屏才能看完右侧的列。把侧栏的收起断点提高，让这一档的内容区拿回宽度；剩下仍然难用的表格逐页处理。只改布局，不动视觉风格和 token。

## 非目标

- 不做视觉打磨、不改 `packages/tokens/tokens.css`、不改配色字体，沿用 FW-016 的 Framed sheet 方向。
- 不做小于 768 的手机浏览器档：管理员在手机上用原生 App（FW-033、FW-034）。
- 不做比例缩放：中文标签和数字有最小可读宽度，按比例缩会折行和断字。
- 不动业务逻辑、路由、数据获取和接口。
- 不改 Mobile 两端。
- 不修演示数据里"12 家店只有 1 家有日程、看板大面积显示 —"的问题，那是演示数据覆盖，归 Backlog「演示」。

## 验收标准

- AC-01（`用户要求`）：`apps/web/src/hooks/use-mobile.tsx` 的收起断点由 768 提到 1024，即宽度小于 1024 时侧栏收成抽屉。1024 及以上保持现在的展开或图标条行为不变。
- AC-02（`用户要求`）：改断点后，先在 768 和 1024 两个宽度逐页截图复核这六个页面的表格：总部看板（门店、店长排行榜、日期趋势三个维度）、账号、门店、模板。每页记录"是否还需要横向滚动、滚多少"。这一步的结论写进 plan，作为 AC-03 的依据。
- AC-03（`用户要求`）：AC-02 判定仍然难用的表格，按这一档的信息密度处理，一页一种做法，在 plan 里写明选了哪种和为什么：次要列收进可展开的行、横向滚动时首列固定、或卡片化。不改表格要显示的字段集合。
- AC-04（`用户要求`）：顶栏在小于 1024 时，管理员与商家身份不折成三行：收成一行（必要时截断并带 title）或收进下拉。
- AC-05（`用户要求`）：这六个页面加登录、注册、审核队列、今日视图、AI 标准、日程方案、门店日程安排、个人中心、通知收件箱，在 768、1024、1440 三个宽度下都没有横向页面滚动（表格自身的横向滚动不算）、没有内容被遮挡、主操作按钮可见可点。
- AC-06（`建议采纳`）：抽屉态的侧栏：打开后焦点进入抽屉、Esc 关闭、关闭后焦点回到触发按钮；遮罩不挡住关闭按钮。
- AC-07（`建议采纳`）：机器门（本单元没有登记 `gate`，在最终代码审查任务里跑并记进证据表）：`pnpm typecheck`、`pnpm lint`、`pnpm format:check`、`pnpm build`、`FW_SLOT=1 pnpm --filter @apps/api test`、Web 界面 e2e。界面 e2e 因选择器失效变红的，改成按角色或文案选元素，不删用例。
- AC-08（`用户要求`）：动代码前把这 15 个页面在 768 和 1440 下各截一张存 `evidence/before/`；交接时给出改动页面的前后对比。

## 验收方式

`A 人工验收`

界面改动，最终由用户在 768、1024、1440 三个宽度逐页看。Agent 跑 AC-07 的机器门、AC-02 的复核截图和代码审查，交接两行后由用户验收。
