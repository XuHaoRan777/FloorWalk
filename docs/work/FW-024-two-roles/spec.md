# 角色收成两层

> ID：`FW-024`
>
> 状态：`approved`

## 目标

接力线一第 1 个。角色只剩商家管理员（一商家一个）和店长（一店可多个、可调店）；店长登录名是邮箱或手机号、昵称由管理员设；同一登录名在多个商家有账号时，登录后选商家。开发库重置。

## 非目标

- 不做邮箱验证码、找回密码（FW-025）。
- 不做个人中心（线二）。
- 不改巡检流程本身：`inspector` 改名为店长后，今日巡检、提交、审核行为照旧，由商家管理员审核。
- 不迁移旧数据，开发库与 e2e 槽位直接按新 schema 重建。

## 验收标准

账号与权限属于认证与权限，失败路径全部由 API 测试取证。

- AC-01（`用户要求`）：角色只有 `admin` 与 `store_manager` 两种；`supervisor` 及主管指派（`site_supervisors`、`PUT /api/admin/sites/:id/supervisor`、Web 指派入口）从契约、schema、接口和界面中删除，不保留备用代码。
- AC-02（`用户要求`）：一个商家有且只有一个 admin，数据库约束保证；`POST /api/admin/users` 建 admin 返回 403；停用 admin 返回 409。
- AC-03（`用户要求`）：admin 建店长：必填登录名（手机号或邮箱，一个字段，按格式校验）、昵称、门店、初始密码（≥8 位），`must_change_password` 为真。登录名在商家内重复 409；格式不对 400；门店属于另一商家 404。店长调用账号管理接口 403。
- AC-04（`用户要求`）：昵称只有 admin 能改（`PATCH /api/admin/users/:id`）；店长本人改昵称的接口不存在或 403。
- AC-05（`用户要求`）：调店：admin 把店长改到另一门店后，店长的今日巡检和新建巡检按新门店；原门店的记录列表和详情只返回他参与过的单（他创建或提交过检查项），其余原门店单 404。
- AC-06（`用户要求`）：登录：`POST /api/auth/session` 用登录名 + 密码。只匹配一个启用账号时直接建会话；匹配多个商家的启用账号时，返回商家列表而不建会话，客户端再带所选商家登录。密码错、账号停用、所选商家不在匹配列表里都 401，且不泄露哪个登录名存在。
- AC-07（`用户要求`）：账号停用、重置密码吊销全部会话，本人改密吊销其他会话，闲置 7 天失效，强制改密拦截，在两层角色下行为不变（沿用现有测试改角色后全部通过）。
- AC-08（`用户要求`）：Web 账号页只建店长，表单含登录名、昵称、门店；门店页去掉主管指派、可看到每店店长列表。Web 与 Mobile 登录页在多商家时显示商家选择。界面 e2e 覆盖：admin 建店长 → 店长首次登录改密 → 进入今日巡检；同一登录名在两个商家时选择商家后进入对应商家。
- AC-09（`建议采纳`）：种子按两层角色重建：Northbean 一个 admin，每店至少一个店长，其中一店两个店长；另建一个与 Northbean 某店长同登录名的第二商家店长，供 AC-06 与 AC-08 取证。开发库与全部 e2e 槽位重置后可用。
