# 自动接力

> FloorWalk：2026-11-04 用户决定后续单元全部单线自动接力；按下文资格排线，不满足资格时逐个开会话。开发环境、测试槽位及起停命令见 [`dev-environment.md`](../context/dev-environment.md)。

建设模式"一单元一会话"的自动衔接：一串串行单元一起批准，前一个到 `verified` 后自动开下一个的会话，用户不用逐个开。不是新模式，单元、验收、授权规则全照 [`AGENTS.md`](../../AGENTS.md)；两条线以上同时做见 [`parallel.md`](parallel.md)。

省下的只是"开会话、贴提示词"这一步，代价是下游 spec 在上游没做时就写定、中间单元做完要挂在 `active` 里等线尾。所以只在这两种情况接力：至少 3 个单元，或至少 2 个连续的方式 B 单元。达不到就逐个开会话，不叫接力。接力线不编号：一起批准看各 spec「批准记录」的接力探针行，上下游看「依赖」和 plan「当前状态」。

## 排线（批准前）

1. 先按每个单元自己的 AC 定验收方式（默认规则见 spec 模板），再排线。不为接力改验收方式，不把一个单元的人工项挪进另一个单元的 AC——挪过去的单元会自称 `verified`，那几条却从没在真实环境验过（校验器 `cross-unit-ac`）。
2. 方式 A 的单元只能在线尾，一条线最多一个；两个都要 A 的不排进同一条线。
3. 下游要消费上游的交付物（配置键所在的模板、接口、文件）时，「依赖」行写单元 ID 和路径，如 `- FW-005：deploy/.env.example`；只写路径，不写内容。
4. 线上单元同时 `active`；超过 `active-units-max` 时，批准时一并取得用户批准改 `scripts/workflow.conf`，记录原值，归档后改回。

## 批准时的环境确认（一次）

批准这条线时逐项确认，结果写进线上每个单元 spec「批准记录」一行：`接力探针（YYYY-MM-DD）：<通过的>；改为用户手动：<不通的>`。

- 提交：常设授权或本次授权覆盖线内本地提交；`commit-msg` 钩子能跑（拿一条样例提交信息直接执行一次）。
- 执行器：能不能开下游会话、在哪个目录开、要不要用户点批准。开不了就写"用户手动开"。
- 本地配置：下游会话在主目录开，拿到的就是同一份 `.env*`；`python scripts/validate_docs.py --env-keys` 不报缺键；若提示没有可检查配置，不能记为通过，按 [开发环境「配置」](../context/dev-environment.md#配置) 先登记，或记录由用户手动核对。

探不通的项在相关 spec 里改成用户手动；因此某个单元要变成方式 A 的，回到排线第 2 条重排。Docker、端口、数据库和外部服务今天通不代表明天通，不在这里一次定，每个单元在 plan 的 Preflight 里自己查。

## 执行

- 在主目录、当前分支上依次做，不建分支、工作树或 tag，同一时刻只有一个单元在做。新工作树里没有被忽略的 `.env*`，主目录已检出的分支也不能在新工作树里再检出。
- 开工：`git log` 确认上游带单元号的提交都在，「依赖」行列的路径都存在，`git status --short` 为空，再从 `plan.md` 当前状态推进。
- 中间单元到 `verified` 后不归档：plan「当前状态」写已交付什么、下游是谁，然后开下游会话，提示词 `执行 <单元号>，自动接力，按 docs/howto/relay.md。`；开不了就回"<单元号> 已完成，下一个是 <单元号>"，由用户手动开。
- 线尾是方式 A：交接两行后停下等用户验收；用户确认后按 [`archive.md`](archive.md) 依次归档本线全部单元。线尾是方式 B：到 `verified` 后直接依次归档。
- 停下：照内核第 7 节的停止条件。在 plan「决策与偏差」写三行（卡在哪、要用户定什么、可选项和倾向），结束会话；无人值守时只靠这三行接上，用户在同一个会话里回复后继续。

接力不放宽内核授权：建单元、改共享契约、真实数据写入、提交、推送各自需要的授权照旧，没有提交授权就记录状态等待。不读取或复制 `.env*` 内容。
