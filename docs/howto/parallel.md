# 并行组（试行）

> 只在 FloorWalk 试行，规则会随试行改；踩坑和每组的数据记在 [`../parallel-trial.md`](../parallel-trial.md)。

并行组只是建设模式下几个单元的排法：模式、验收方式 A/B、单元生命周期都照 `AGENTS.md`。不是第三种工作模式，修正模式不用它。

一组单元按角色分：

| 角色     | 个数          | 在哪做             | 验收方式 | 和普通单元的不同                                           |
| -------- | ------------- | ------------------ | -------- | ---------------------------------------------------------- |
| 契约单元 | 1，开组前归档 | 主目录             | 照常定   | 多交付契约代码、骨架、演示链 e2e、跨端最薄链路（第 1 节）  |
| 并行单元 | 最多 3        | 各自的工作树和分支 | 照常定   | 有写入范围，契约只读；做完不归档，打完成标记（第 3、4 节） |
| 集成单元 | 1             | 主目录             | 固定 B   | 只做合并、门禁、演示链 e2e、交付与归档（第 6 节）          |

plan「当前状态」下的「并行组」那一行写明本单元属于哪组、什么角色；没有这一行的就是普通单元。每个并行单元各占一个 Codex 对话；合并后用户在主目录一次测完。

名字（以 g01 组为例，组号用两位数字）：

| 名字                 | 是什么                           | 谁建                   |
| -------------------- | -------------------------------- | ---------------------- |
| `g01/start`          | tag，契约单元归档后的 master     | 用户或开组的会话       |
| `g01/FW-NNN`         | 并行单元的分支                   | 该单元，对话的第一步   |
| `g01/done/FW-NNN`    | tag，该单元做完                  | 该单元                 |
| `g01/blocked/FW-NNN` | tag，该单元停下等用户（第 3 节） | 该单元打，用户答复后删 |
| `g01/close`          | tag，开集成对话的锁              | 最后做完的那个单元     |

分支和 tag 不能同名：同名时 git 优先解析 tag，合并就会漏掉 tag 之后的提交。

## 0. 准入与切法

开组前先过准入，三条有一条不满足就串行，不硬上（依据见 [试行记录](../parallel-trial.md) g01 各条）：

1. 本组要用户定的产品语义，开组前全部定掉；定不了的那项不进本组。g01 的 FW-004 停下问演示脚本，并行单元无人值守，停下就是空等。
2. 每个并行单元交付的关键路径，都能在本机由机器验证；Mobile 原生路径要有模拟器。g01 的 Mobile 只验了 Expo Web，原生上传的两个 bug 到真机才暴露。
3. 写入范围按文件能分开：每个单元新增自己的文件，共享文件只加注册行（路由、导航、模块列表、契约导出）。几个单元要改同一个大文件的，先开一个普通单元按功能拆模块，再开组。

切法默认竖切：一个并行单元交付一个功能的全部端（API、Web、Mobile），各端代码放在该功能自己的模块里。g01 按端横切，写入范围零交叉，代价是契约面最大、跨端问题全部推到集成才暴露（4 个 bug 里 3 个是这样）。竖切的单元之间只共享已有表和登录，契约单元只定本组共用的部分。注册行冲突由集成单元按 T01 解，计入冲突数。

模拟器按槽位分：每个要做原生取证的并行单元用自己槽位的模拟器（AVD 名带槽位号，`adb -s` 指定设备）。开组前在第三道门里确认这几台能同时开起来；开不起来，本组只允许一个并行单元有原生取证，其余的留到集成单元 T03，在它们的 spec 里写明。

## 1. 开组前：契约单元

契约单元是普通单元，照常讨论、批准、归档；一组可以有不止一个，开组前发现契约偏了就再开一个修订单元，不在并行期间修。契约内容在讨论阶段和用户一起定：表结构、枚举、状态迁移、接口与参数、错误码、角色权限。定下的内容写进 spec 的「契约」节，用户批准 spec 就是批准契约，实现照 spec 来，不多不少。交付七样：

1. 契约代码：放在 `@libs/shared`，是 spec「契约」节的代码形式（schema、类型、路由表、状态迁移表、权限表），只写形状和规则，不写实现。目录在 spec 里定，归档时登记进 `scripts/workflow.conf` 的 `hardline`；Promote 时契约写进 `docs/specs/`，此后以那里为准。
2. 表和迁移：本组要用的表一次建好，并行单元不加迁移。
3. 依赖：本组要用的依赖一次装好。几个分支各自加依赖，合并时 `pnpm-lock.yaml` 必然冲突。
4. 骨架：所有契约接口都能调用，返回符合 schema 的固定数据；迁移、登录与角色、照片存储能跑；e2e 按槽位号选库和端口，能在槽位库里跑起来。进程环境变量优先于 env 文件，所以槽位的库名和端口用环境变量传。
5. 演示链 e2e（API 层）：按 [产品基线](../context/product.md) 的演示流程直接调接口写成测试，开组时允许是红的。界面层由各端并行单元在自己的 e2e 里写，开发时连骨架，集成后连真接口（第 6 节 T03）。
6. 跨端最薄链路：本组每个跨端功能，在骨架上走通一次最短的端到端（如 Mobile 在模拟器上发一条、Web 看到、再回到 Mobile），各端界面可以简陋，但要用真实的平台 API（原生选图、原生请求）。g01 的平台判断和 FormData 两个 bug 都出在"骨架能调、原生端从没跑过"，这一步在开组前就能抓到。
7. 预授权：spec「批准记录」写明并行单元可自行处理的小偏差（如契约单元写的测试脚本漏步骤，可在本分支补，不算契约改动），其余照第 5 节停下。g01 的 FW-004 为演示脚本漏一次 `start` 停下等了一夜。

打 tag `g01/start` 前，过三道门。机器门全绿不能代替它们：g01 的契约单元测试全绿，但三道门各查出了问题（[试行记录](../parallel-trial.md)）。三道门由契约单元最后一个任务执行，也可以由用户另找一个上下文执行。

1. 按流程走路由表：逐个并行单元，把它的用户流程一步步对到路由表上：调哪个接口、需要的字段响应里有没有、这个角色能不能调。哪一步对不上，就是契约缺口。演示链脚本的每一步审核动作也对照状态迁移表核一遍。g01 用这道门查出了打回信息拿不到、门店名拿不到；没核脚本，漏了一次 `start`，到并行时才暴露。
2. 新库实测：重置一个槽位，起 API，用真请求核对种子不变量和每个接口的响应，不只看测试。g01 用这道门查出了缺 `/api` 前缀、分数与检查项不符、照片文件不存在。
3. 并发隔离：三个槽位同时跑全部测试命令，确认都通过；前后对比开发库，确认没有被清空重灌；不设 `FW_SLOT` 时每条命令都报错退出。

三道门之外，在 master 上跑一次全量门禁（类型检查、lint、`format:check`、构建）。修正模式只跑类型检查和对应测试，格式问题会留在 master 上，到并行单元那里就成了"别人的失败"。

三道门都过了，用户按各端 `.env*.example` 补齐主目录的 env 文件（新建工作树时会复制它们，补晚了工作树里就是旧的），再在主目录打 tag `g01/start`。之后才在主目录提交的东西（比如并行单元的 spec），要把 tag 重打到最新提交，让 `g01/start` 始终是开组时的 master。

## 2. 开并行单元

- 3 个并行单元和集成单元的 spec、plan 先在主目录一起写、一起批，登记 Backlog，提交到 master。
  - 并行单元 spec 的「依赖」写契约单元的 ID；「批准记录」的特殊授权写 `并行组 g01，写入范围：<目录或包>；在本分支本地提交，不推送`。
  - 两个单元的写入范围不能交叉，交叉就合成一个单元或改成串行。
  - 每个 plan 的「当前状态」下加一行，例：并行单元写 `- 并行组：g01，并行单元，槽位 1（并行 FW-004、FW-005、FW-006；集成 FW-007）`，集成单元写 `- 并行组：g01，集成单元（并行 FW-004、FW-005、FW-006）`。槽位取 1～3，各单元不同。
- 每个并行单元开一个 Codex 对话：工作位置选「新建本地工作树」，起点分支选 master，权限选完全访问。第一条消息：

  ```text
  执行 FW-NNN，它属于并行组 g01，按 AGENTS.md 和 docs/howto/parallel.md。先跑 git rev-parse --git-dir 和 git rev-parse --git-common-dir：两者相同说明你在主目录，停下告诉我，不切分支、不自建工作树。不同再 git switch -c g01/FW-NNN，然后 pnpm install --frozen-lockfile。
  ```

## 3. 并行单元的规则

- 只在 Codex 建的工作树里做：发现在主目录（`git rev-parse --git-dir` 与 `--git-common-dir` 相同）就停下，等用户重开对话；不切主目录的分支，不用 `git worktree add` 自建工作树（自建的不归 Codex 管，env 文件也不全）。
- 只改本单元 spec 写的写入范围。契约目录只读：契约错了或不够用，停下报告，由用户决定改不改（见第 5 节），不自己改，也不在本单元里绕开契约。
- `plan.md` 只在自己的分支上改。`docs/backlog.md` 只改「当前工作」里本单元那一行的状态（校验器要求它和 plan 一致）。`docs/specs/`、`docs/pitfalls.md`、`docs/adr/` 和 Backlog 其他表都不改，留给集成单元。
- e2e 用自己的槽位 N：库 `floorwalk_e2e_N`，端口 API `31N0`、Web `31N1`、Metro `31N2`（槽位 1 就是 3110、3111、3112）。所有带 `FW_SLOT` 的命令只用自己的槽位号；不跑 `pnpm e2e:slots`，它会重置三个槽位的库，冲掉别的单元正在跑的测试（留给集成单元）。不跑 `pnpm dev`，不占 3018～3020。测试结束关掉自己起的进程。
- 不加依赖、不加迁移；确实要加，停下报告，按第 5 节处理，等同改契约。
- 只在本地提交，不推送；不 merge、不 rebase 别的单元的分支。
- 要停下等用户时（本节和第 5 节的停止条件，或 AGENTS.md 第 7 节），先在 plan「决策与偏差」写三行：卡在哪一步、要用户定什么、可选项和你的倾向；提交后打 tag `g01/blocked/FW-NNN`，再结束对话。用户用 `git tag --list "g01/blocked/*"` 看谁在等，答复后删掉这个 tag，在同一对话里继续。
- 什么叫做完：
  - 最终审查必须交给独立 Subagent（`docs/howto/final-review.md`），不接受"共享工作树""上下文不便"这类改成同会话审查的理由。g01 的两个同会话审查，改由独立上下文重审后，一共多查出 6 条（[试行记录](../parallel-trial.md)）。
  - 方式 B：AC 全绿、最终审查过了，状态 `verified`。
  - 方式 A：机器门、第 14 节失败路径测试、最终审查都过了，plan「交接」两行写好，人工那行证据标 `blocked`。不登记「待人工验收」，用户在合并后统一测。
- 做完后不归档，`归档状态` 保持 `active`；提交后执行第 4 节。

## 4. 完成标记与开集成对话

在工作树里依次执行：

```bash
git tag g01/done/FW-NNN
git tag --list "g01/done/*"
```

- 和 plan「并行组」那行列出的并行单元比，还没齐：结束本对话，说"等其他单元"。先打 tag 再查，两个单元同时做完时，至少有一个能看到齐了。
- 已经齐了：执行 `git tag g01/close`。
  - 成功：用 `create_thread` 开集成对话，工作位置选本地（主目录），提示词写"执行 FW-<集成单元号>，并行组 g01 的集成单元，按 docs/howto/parallel.md 第 6 节"。app 可能弹一次审批，用户点批准。然后结束本对话。
  - 报 already exists：别的单元已经抢到，结束本对话。

## 5. 契约要改时

并行单元停下，由用户决定：

- 改：用户批准后，在主目录同时改契约代码和 `docs/specs/` 里的契约小节，提交到 master（提交信息带集成单元号和「硬线：」行），并在集成单元 plan「决策与偏差」写一行。各单元在自己的分支上 `git merge master`，只合契约这一次。
- 不改：单元按现有契约做，契约覆盖不到的部分在本单元「决策与偏差」写一行，开后续单元。

每次改契约都记进试行记录。

## 6. 集成单元

集成单元在主目录、master 上执行，验收方式固定 B（它的 AC 全是机器能验的）。spec 的「依赖」写本组 3 个并行单元；AC 只写本单元自己的事。任务表如下；本组额外的任务（如 g01 的跨端界面演示链）排在「交付与归档」之前，编号顺延：

| 任务             | 做什么                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T01 合并         | 按单元号顺序 `git merge --no-ff g01/FW-NNN`。每次合并前跑 `git diff --stat g01/start g01/FW-NNN -- <契约目录> <schema 文件> <迁移目录> "**/package.json" pnpm-lock.yaml`（路径照 `scripts/workflow.conf` 的 hardline 填）：有改动、又不是第 5 节批准的，停下报告。`docs/backlog.md` 几乎每次都冲突（相邻行各改一行），不算进冲突数：取 master 的版本，再把刚合并的单元那一行改成它分支上的状态。不要用 union 合并，它会留下重复行。`pnpm-lock.yaml` 冲突时（第 5 节批准过加依赖），先解 `package.json`，再跑 `pnpm install` 重新生成锁文件。其他冲突只会出在两个单元都改过的文件里，解法写进本单元 plan。 |
| T02 全量门禁     | 类型检查、lint、构建、全量测试各一次，失败按第 7 节归属修。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| T03 演示链 e2e   | 起真 API，跑 API 层演示链和各端的界面 e2e，全绿算通过。并行单元的界面 e2e 是对着骨架固定数据写的，换成真接口后失败的，按第 7 节归属修。                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| T04 交付与归档   | 并行单元留下的人工项（方式 A 的「需要你测的」，方式 B 里机器验不了的部分）登记到「待人工验收」，告诉用户在主目录按 [本地启动](local-development.md) 测，反馈按第 7 节修。用户确认一个就归档一个（[`archive.md`](archive.md)），没有人工项的直接归档。                                                                                                                                                                                                                                                                                                                                                     |
| T05 最终代码审查 | 只审本单元自己的改动：合并冲突的解法和第 7 节记在本单元的修复。都没有，就在证据行写"不适用，无自身改动"。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

本单元 `verified` 后照常归档，归档时在试行记录追加本组一段。集成单元总是本组最后一个归档。

「交付与归档」归档并行单元时有一处和 `archive.md` 不同：对账的范围是它分支上的提交（`git log g01/start..g01/FW-NNN`），加上合并后 master 上带它单元号的回修提交。

## 7. 合并后出的问题

- 能定位到某个并行单元的，算那个单元的回修：记进它 `plan.md` 的「回修」，提交信息写那个单元号。
- 定位不了的（几个单元组合出的问题、契约本身漏了），记进集成单元的「决策与偏差」，由用户决定开后续单元还是当场修；当场修的提交写集成单元号。
- 集成单元不替并行单元补证据。并行单元缺证据不能归档，回到那个单元的分支由它补齐，再重新合并。

## 8. 收组

- 4 个单元都归档后，本组的分支和 tag 删不删由用户决定。不是 Codex 建的工作树，Codex 归档对话时不会删，收组时用 `git worktree remove` 手动删。Codex 归档那 3 个对话时会删掉对应的工作树，所以集成单元完成前不要归档它们。
- 不再并行时，把 `scripts/workflow.conf` 的 `active-units-max` 改回 3。
