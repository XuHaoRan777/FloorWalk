# 并行组（试行）

> 只在 FloorWalk 试行，适用于中小型项目；规则会随试行改，踩坑和每组的数据记在 [`../parallel-trial.md`](../parallel-trial.md)。2026-10-30 按 g02 复盘和用户的新构想重写：协议阶段集中定共享模块和全部接口，按"线"排单元，单元做完自动开下一个。

并行组只是建设模式下几个单元的排法：模式、验收方式 A/B、单元生命周期都照 `AGENTS.md`。不是第三种工作模式，修正模式不用它。

## 概念

- **组**（`gNN`，两位数字）：从协议单元到集成单元的一批单元。
- **线**：一串串行单元，共用一个分支（`gNN/L1`～`L3`）、一个工作树、一个测试槽位。同一时间最多 3 条线（只有 3 个测试槽位）；一条线 1～3 个单元。只有一条线的组，就是自动接力的串行链。
- **角色**：

| 角色     | 个数           | 在哪做             | 验收方式 | 做什么                                                |
| -------- | -------------- | ------------------ | -------- | ----------------------------------------------------- |
| 协议单元 | 1，开组前归档  | 主目录             | 照常定   | 定共享模块、全部接口、环境清单，开组（第 1、2 节）    |
| 线上单元 | 每条线 1～3 个 | 本线的工作树和分支 | 照常定   | 做一个功能点；做完开下游或集成（第 3、4 节）          |
| 集成单元 | 1              | 主目录             | 固定 B   | 合并、全量测试、用户能直接启动、清理、归档（第 6 节） |

| 名字                 | 是什么                | 谁建                     |
| -------------------- | --------------------- | ------------------------ |
| `gNN/start`          | tag，开组时的 master  | 协议单元，用户说"开组"后 |
| `gNN/L1`～`L3`       | 线的分支              | 协议单元开组时建         |
| `gNN/blocked/FW-NNN` | tag，该单元停下等用户 | 该单元打，用户答复后删   |
| `gNN/done/FW-NNN`    | tag，该单元做完       | 该单元                   |
| `gNN/close`          | tag，开集成对话的锁   | 最后完成的线尾单元       |

分支和 tag 不能同名：同名时 git 优先解析 tag。

## 0. 准备阶段

和用户讨论业务逻辑，拆成功能点，每个功能点一个单元。产品语义在这一阶段全部定掉：线上单元无人值守，停下就是空等。每个功能点标一类：

- 可并行：写入范围能按文件和别的功能分开，不依赖本组其他功能新建的数据。
- 必须串行：横切的（认证、权限、改共用表结构），排在组前或组后的普通单元里。
- 原生：要在模拟器上取证。本机只有一台模拟器，原生单元都排在同一条线上。

排线的规矩：

1. 依赖只在线内。A2 依赖 A1 可以；B2 依赖 A1 不行，两个有依赖的功能排进同一条线。
2. 每条线不超过 3 个单元。功能更多就分两组，第二组的协议阶段吸收第一组的坑。
3. 要人工验收（方式 A）的单元只放线尾，或者改成方式 B、人工项留到收尾。线中间的单元必须能自己到 `verified`，接力才不断。
4. 线和线之间写入范围不交叉；几个功能要改同一个大文件的，先开普通单元按功能拆开（g02 前的 FW-008）。

## 1. 协议阶段：协议单元

协议单元是普通单元，照常讨论、批准、归档。讨论用对话、自底向上：数据表 → 枚举 → 实体类型 → 公用方法 → 按功能点列出接口、参数和响应类型。讨论时过一遍检查清单（踩坑后往里补，依据见试行记录）：

- 每个功能的用户流程逐步对到接口上：要哪些字段、这个角色能不能调（g01 缺打回信息和门店名）。
- 每条接口的权限、错误码、分页和排序规则；时间戳的精度（FW-011 的毫秒游标）。
- 数量和取值类要求先确认可满足，写清"合计"还是"每项"（g01 种子分数）。
- 跨功能共用的组件和它的参数（g02 的 `ChatPanel`）。

交付：

1. 共享模块：本组的表和迁移、依赖一次装好；枚举、实体类型、公用方法；每个功能一个契约文件 `packages/shared/src/contract/<功能>.ts` 写它的接口，`index.ts` 导出。线上单元不改共享模块。
2. 注册行和空桩：控制器注册、两端 `lib/api.ts` 的导出、页面和 Tab/分区、跨功能组件的空桩，各指向线上单元自己的文件。
3. 写入范围：按线逐个文件列出。
4. 线上单元和集成单元的 spec、plan，和协议单元一起批准，登记 Backlog；`scripts/workflow.conf` 的 `active-units-max` 改成它们的总数加 1（校验器按 `active` 单元计数）。plan「当前状态」写 `- 并行组：gNN，线 L1 第 2 个（上游 FW-A，下游 FW-C），槽位 1`；集成单元写 `- 并行组：gNN，集成单元（线尾 FW-C、FW-E、FW-F）`。
5. 环境清单，写进协议单元 spec 的「环境」一节，逐条定好：
   - 环境变量：各端要新增或用到的键名，主目录 env 里有没有（只核对名字）。
   - 数据库：槽位库 1～3 就绪；开发库要不要迁移到本组的表（收尾时用）。
   - 端口与进程：每条线的槽位；原生线是哪一条。
   - 测试环境：g02 修过的项仍在（UI 套件 `workers` 为 1、图片断言用 `naturalWidth`）。
   - 要用户明文授权的：改硬线路径、加依赖或迁移、写开发库、起常驻进程（如 Metro）、删文件、推送。写进相关单元 spec 的「批准记录」，并行期间不再问。
   - 探针：本组用到、又没在本机验证过的执行入口，在协议单元后段视情况试一次（如 `create_thread` 开出的对话能否起 Metro、能否开在已有分支上）。不通过的，在相关 spec 里改成用户手动。
6. 开组检查：在 master 上跑通类型检查、lint、`format:check`、构建、`FW_SLOT=1 pnpm --filter @apps/api test`、`pnpm e2e:slots`。

## 2. 开组

协议单元归档后停下，告诉用户可以开组。用户在同一个对话里说"开组"，它依次：

1. 确认工作区干净、主目录各端 env 文件齐全（新建工作树按 `.worktreeinclude` 复制），打 `gNN/start`。
2. 为每条线建分支：`git branch gNN/L1 gNN/start`。
3. 用 `create_thread` 为每条线的第一个单元开对话：工作树环境，起点分支 `gNN/Lk`，完全访问，提示词见下。每次可能弹一次审批，用户点批准。探针不通过时，改为把三条提示词交给用户手动开（工作位置「新建本地工作树」，起点分支选对应的线）。

```text
执行 FW-NNN，并行组 gNN 线 Lk，槽位 N，按 AGENTS.md 和 docs/howto/parallel.md 第 3、4 节。先确认 git rev-parse --git-dir 与 --git-common-dir 不同（相同说明在主目录，停下告诉用户）、当前分支是 gNN/Lk；然后 pnpm install --frozen-lockfile。
```

推送不是开组的前提：工作树都在本机、共用一个仓库。

## 3. 线上单元的规则

- 只在本线的工作树和分支上做；发现在主目录就停下，不切主目录的分支、不自建工作树。下游单元开工先 `git log` 确认上游的提交都在。
- 只改 spec 写的写入范围；共享模块、契约文件只读，不够用就停下按第 5 节。
- `plan.md` 只在本线分支上改；`docs/backlog.md` 只改「当前工作」里本单元那一行；`docs/specs/`、`docs/pitfalls.md`、`docs/adr/` 留给集成单元。
- 只用本线的槽位 N：库 `floorwalk_e2e_N`，端口 API `31N0`、Web `31N1`、Metro `31N2`。不跑 `pnpm e2e:slots`、`pnpm dev`，不占 3018～3020；同槽位套件串行跑，测完按端口关掉自己起的进程。
- 不加依赖、不加迁移，只在本地提交，不推送，不合并别的线。
- 不用停、直接处理的：本单元新写测试的定位、等待问题；上游或协议单元写的测试漏了步骤；原有不稳定测试只改定位、不放宽断言。改动写进证据。实现上的 bug，同一个失败可以修两轮，第二轮前先做区分实验。
- 要停下的：要用户定产品语义；要改写入范围外的文件、共享模块、依赖或迁移；同一个失败修了两轮仍解释不了。停下时在 plan「决策与偏差」写三行（卡在哪、要用户定什么、可选项和倾向），提交，打 `gNN/blocked/FW-NNN`，结束对话。用户直接在这个对话里回复，删 tag 后继续。
- 做完：最终审查交给独立 Subagent（`docs/howto/final-review.md`）；方式 B 到 `verified`，方式 A（只在线尾）写好交接两行、人工那行标 `blocked`。不归档，执行第 4 节。

## 4. 做完与接力

1. 打 `gNN/done/FW-NNN`。
2. 本单元有下游：用 `create_thread` 开下游对话，工作树环境，起点分支 `gNN/Lk`（本线），提示词同第 2 节，换成下游的单元号。然后结束本对话。
3. 本单元是线尾：`git tag --list "gNN/done/*"` 与集成单元 plan 列出的线尾比，没齐就结束对话；齐了执行 `git tag gNN/close`。成功：用 `create_thread` 开集成对话，工作位置本地（主目录），提示词"执行 FW-<集成单元号>，并行组 gNN 的集成单元，按 docs/howto/parallel.md 第 6 节"。报 already exists：别的线已经抢到，结束对话。

`create_thread` 用不了（探针不通过或被拒）时，结束对话并回一句"FW-NNN 已完成，下一个是 FW-MMM"，由用户手动开。

## 5. 契约要改时

线上单元停下，由用户决定。改：用户批准后在主目录改共享模块和 `docs/specs/` 对应小节，提交到 master（带集成单元号和「硬线：」行），各线在自己分支上 `git merge master`，只合这一次。不改：单元按现有契约做，覆盖不到的部分在「决策与偏差」写一行，开后续单元。每次改都记进试行记录。

## 6. 收尾阶段：集成单元

在主目录 master 上执行，验收方式固定 B。写入范围默认包括合并冲突涉及的文件、`tests/`、`playwright.*.config.ts`、`scripts/demo-chain.mjs` 和 docs。任务：

| 任务               | 做什么                                                                                                                                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| T01 合并           | 按线号顺序 `git merge --no-ff gNN/Lk`，提交信息带集成单元号。合并前跑 `git diff --stat gNN/start gNN/Lk -- <hardline 路径>`：有改动又不是第 5 节批准的，停下报告。`docs/backlog.md` 冲突不计数：取 master 版本，再改刚合并那几个单元的行。 |
| T02 全量测试       | 类型检查、lint、构建、`FW_SLOT=1 pnpm --filter @apps/api test`、`pnpm e2e:slots`、各端界面 e2e、`e2e:cors`、`e2e:demo`。                                                                                                                   |
| T03 跨端回归       | 本组新增的跨端路径写进 `e2e:demo-ui`（每个角色独立 `browser.newContext()`）；有原生路径的在模拟器上回归一次。                                                                                                                              |
| T04 用户能直接启动 | 按环境清单的授权把开发库迁移到最新；在主目录 `pnpm dev` 起三端，API `/health` 200、Web 3019 能登录、Expo Go 能连上，然后停掉；在 plan「交接」写三行启动说明给用户。                                                                        |
| T05 交付与归档     | 人工项登记「待人工验收」，用户确认后归档；其余按线、线内顺序归档。对账范围是 `git log gNN/start..gNN/Lk` 里带该单元号的提交，加上 master 上带该单元号的回修。                                                                              |
| T06 清理与审查     | 逐项确认已停：3018～3020、3110～3132 无监听，模拟器已关，`adb reverse --list` 为空，没有本组起的 Metro；写进证据。独立审查只审本单元的改动；在试行记录写本组的数；归档本单元。                                                             |

## 7. 合并后出的问题

- 能定位到某个线上单元的，算它的回修：记进它 `plan.md` 的「回修」，提交写它的单元号。
- 定位不了的（几条线组合出的问题、测试设施、共享模块漏了），记进集成单元的「决策与偏差」，当场修的提交写集成单元号。
- 集成单元不替线上单元补证据：缺证据的回到那条线的分支补齐，再重新合并。

## 8. 收组

- 集成单元归档后，用户决定删不删本组的分支、tag 和工作树。Codex 归档对话时会删它的工作树，集成单元完成前不要归档线上的对话。
- `scripts/workflow.conf` 的 `active-units-max` 改回 3。
