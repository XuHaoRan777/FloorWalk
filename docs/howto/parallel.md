# 并行组与自动接力

> FloorWalk：单元号前缀 `FW`；测试槽位、端口、起停脚本的服务和新工作树取 env 的方式见 [`dev-environment.md`](../context/dev-environment.md)「测试槽位」；g01～g03 的每组数据与踩坑在 [`../parallel-trial.md`](../parallel-trial.md)。2026-11-04 起本项目后续单元全部单线自动接力（用户决定）。

建设模式下几个单元的排法，不是第三种工作模式，修正模式不用它。模式、验收方式 A/B、单元生命周期照 `AGENTS.md`。

两种用法：

- **自动接力**（只有一条线）：一串串行单元，前一个做完自动开下一个，用户不用逐个开对话。没有协议单元和集成单元，第 1 节只做"线上单元的 spec 一起批准"，第 6 节不做。
- **并行组**（两条线以上）：协议单元先定共享模块和全部接口，几条线同时做，集成单元合并收尾。

并行组在单人 + Agent 项目里没证明省人工：三组试行，人工触点按单元平均都没低于串行基线，省下的时间被协议和集成两个单元吃掉。用之前先想清楚是为了"不用守着开对话"，还是为了"更快"——后者没有证据。接力和下面的分支交接、进程脚本在单线时同样有用。

## 概念

- **组**（`gNN`，两位数字）：一次一起批准、一起收尾的一批单元。
- **线**：一串串行单元，共用一个分支（`gNN/L1`～`Lk`）、一个工作树、一个测试槽位。线数不超过测试槽位数；一条线 1～3 个单元。
- **角色**：

| 角色     | 个数             | 在哪做             | 验收方式 | 做什么                                                |
| -------- | ---------------- | ------------------ | -------- | ----------------------------------------------------- |
| 协议单元 | 并行组 1，接力 0 | 主目录             | 照常定   | 定共享模块、全部接口、环境清单，开组（第 1、2 节）    |
| 线上单元 | 每条线 1～3 个   | 本线的工作树和分支 | 照常定   | 做一个功能点；做完开下游或集成（第 3、4 节）          |
| 集成单元 | 并行组 1，接力 0 | 主目录             | 固定 B   | 合并、全量测试、用户能直接启动、清理、归档（第 6 节） |

| 名字                               | 是什么                | 谁建                   |
| ---------------------------------- | --------------------- | ---------------------- |
| `gNN/start`                        | tag，开组时的主分支   | 用户说"开组"后         |
| `gNN/L1`～`Lk`                     | 线的分支              | 开组时建               |
| `gNN/blocked/<WORK_ID_PREFIX>-NNN` | tag，该单元停下等用户 | 该单元打，用户答复后删 |
| `gNN/done/<WORK_ID_PREFIX>-NNN`    | tag，该单元做完       | 该单元                 |
| `gNN/close`                        | tag，开集成对话的锁   | 最后完成的线尾单元     |

分支和 tag 不能同名：同名时 git 优先解析 tag。

## 0. 准备阶段

和用户讨论业务逻辑，拆成功能点，每个功能点一个单元。产品语义在这一阶段全部定掉：线上单元无人值守，停下就是空等。用户说"按默认"的，等于 Agent 替用户做了产品决定——业务用户自己没想清楚时，先补业务，不开组。每个功能点标一类：

- 可并行：写入范围能按文件和别的功能分开，不依赖本组其他功能新建的数据。
- 必须串行：横切的（认证、权限、改共用表结构），排在组前或组后，或排进同一条线。
- 独占设备：要在唯一一台模拟器、真机或外部沙箱上取证的，都排在同一条线上。

排线的规矩：

1. 依赖只在线内。A2 依赖 A1 可以；B2 依赖 A1 不行，两个有依赖的功能排进同一条线。
2. 每条线不超过 3 个单元。功能更多就分两组。
3. 要人工验收（方式 A）的单元只放线尾，或改成方式 B、人工项留到收尾。线中间的单元必须能自己到 `verified`，接力才不断。
4. 线和线之间写入范围不交叉；几个功能要改同一个大文件的，先开普通单元按功能拆开。

## 1. 协议阶段：协议单元

协议单元是普通单元，照常讨论、批准、归档。讨论自底向上：数据表 → 枚举 → 实体类型 → 公用方法 → 按功能点列出接口、参数和响应类型。讨论时过一遍检查清单，踩坑后往项目自己的这份清单里补：

- 每个功能的用户流程逐步对到接口上：要哪些字段、这个角色能不能调。
- 每条接口的权限、错误码、分页和排序规则；时间戳的精度。
- 数量和取值类要求先确认可满足，写清"合计"还是"每项"。
- 跨功能共用的组件和它的参数。
- 现有约束（唯一索引、检查约束）和现有路由的角色，按本组的新产品语义逐条重核；只列新增的，旧的全局约束会漏改。
- 每条 AC 要求的能力，写入范围里都有能实现它的文件。

交付：

1. 共享模块：本组的表和迁移、依赖一次装好（版本固定）；枚举、实体类型、公用方法、每个功能的接口契约。线上单元不改共享模块。
2. 注册行和空桩：路由或控制器注册、客户端导出、页面和导航入口、跨功能组件的空桩，各指向线上单元自己的文件；新接口可以先返回 501，契约测试对 501 只检查角色。
3. 写入范围：按线逐个文件列出。
4. 线上单元和集成单元的 spec、plan，和协议单元一起批准，登记 Backlog；`scripts/workflow.conf` 的 `active-units-max` 改成它们的总数加 1。plan「当前状态」写 `- 并行组：gNN，线 L1 第 2 个（上游 A，下游 C），槽位 1`；集成单元写 `- 并行组：gNN，集成单元（线尾 C、E、F）`。
5. 环境清单，写进协议单元 spec 的「环境」一节：
   - 环境变量：各端要新增或用到的键名，主目录 env 里有没有（只核对名字）。
   - 数据库与存储：每个槽位的库和存储目录就绪；开发库要不要迁移到本组的表（收尾时用）。
   - 端口与进程：每条线的槽位；独占设备在哪条线。常驻进程用项目的起停脚本，本组要的服务脚本里没有的，由协议单元加进去并实测一次起停。
   - 要用户明文授权的：改硬线路径、加依赖或迁移、写开发库、调用真实外部服务、删文件、推送。写进相关单元 spec 的「批准记录」，并行期间不再问。
   - 探针：本组用到、又没在本机验证过的外部入口（模型、对象存储、执行器能力），在协议单元后段各试一次，用内容已知的输入，结果写进证据。不通过的，在相关 spec 里改成用户手动。
6. 开组检查：在主分支上跑通类型检查、lint、格式检查、构建、各槽位的测试命令。

## 2. 开组

协议单元归档后停下，告诉用户可以开组。用户在同一个对话里说"开组"，它依次：

1. 确认工作区干净、主目录各端 env 文件齐全，打 `gNN/start`。
2. 为每条线建分支：`git branch gNN/L1 gNN/start`。
3. 为每条线的第一个单元开对话：在新工作树里，起点 `gNN/Lk`，提示词用下面的「线上单元」。执行器能开对话就自己开；开不了就把各线的提示词交给用户手动开。

两条提示词与执行器无关，换执行器直接贴（安装依赖那一步换成项目的命令）：

```text
线上单元：执行 <单元号>，并行组 gNN 线 Lk，槽位 N，按 AGENTS.md 和 docs/howto/parallel.md 第 3、4 节。先确认 git rev-parse --git-dir 与 --git-common-dir 不同（相同说明在主目录，停下告诉用户），再 git switch gNN/Lk（失败就停下告诉用户）；然后安装依赖。
```

```text
集成单元：执行 <单元号>，并行组 gNN 的集成单元，在主目录主分支上，按 docs/howto/parallel.md 第 6 节。
```

新工作树是游离 HEAD，起点只决定从哪个提交开始，不会检出分支；同一分支不能同时检出在两个工作树里，所以线上单元开工 `git switch`、做完 `git switch --detach` 把分支让给下游。推送不是开组的前提：工作树都在本机、共用一个仓库。新工作树里拿不到被忽略的文件（env、本地配置），要靠执行器的复制机制或用户手动放进去。工作树建在哪由执行器的全局设置决定，不能按项目配：建在项目内的（如 `<repo>/.claude/worktrees`）要在 `.gitignore` 里忽略，建在用户目录的最好改到非系统盘。

## 3. 线上单元的规则

- 只在本线的工作树和分支上做；发现在主目录就停下，不切主目录的分支、不自建工作树。下游单元开工先 `git log` 确认上游的提交都在。
- 只改 spec 写的写入范围；共享模块、契约只读，不够用就停下按第 5 节。
- `plan.md` 只在本线分支上改；`docs/backlog.md` 只改「当前工作」里本单元那一行；`docs/specs/`、`docs/pitfalls.md`、`docs/adr/` 留给集成单元。
- 只用本线的槽位：库、存储目录、端口都按项目 dev-environment 的槽位规则；不跑占用全部槽位或开发端口的命令；同槽位套件串行跑。常驻进程用起停脚本起停，结束对话前 `stop`。
- 不加依赖、不加迁移，只在本地提交，不推送，不合并别的线。
- 不用停、直接处理的：本单元新写测试的定位、等待问题；上游或协议单元写的测试漏了步骤；原有不稳定测试只改定位、不放宽断言。改动写进证据。实现上的 bug，同一个失败可以修两轮，第二轮前先做区分实验。
- 要停下的：要用户定产品语义；要改写入范围外的文件、共享模块、依赖或迁移；同一个失败修了两轮仍解释不了。停下时在 plan「决策与偏差」写三行（卡在哪、要用户定什么、可选项和倾向），提交，打 `gNN/blocked/<单元号>`，结束对话。用户直接在这个对话里回复，删 tag 后继续。
- 做完：最终审查交给独立 Subagent（`docs/howto/final-review.md`）；方式 B 到 `verified`，方式 A（只在线尾）写好交接两行、人工那行标 `blocked`。不归档，执行第 4 节。

## 4. 做完与接力

1. 确认改动都已提交，打 `gNN/done/<单元号>`，然后 `git switch --detach` 让出 `gNN/Lk`。
2. 本单元有下游：开下游对话，在新工作树里，起点 `gNN/Lk`，提示词用第 2 节的「线上单元」，换成下游的单元号。然后结束本对话。
3. 本单元是线尾：
   - 自动接力（只有一条线）：线尾按 `docs/howto/archive.md` 依次归档本线全部单元，`active-units-max` 改回，结束。
   - 并行组：`git tag --list "gNN/done/*"` 与集成单元 plan 列出的线尾比，没齐就结束对话；齐了执行 `git tag gNN/close`。成功：开集成对话，工作位置本地主目录，提示词用第 2 节的「集成单元」。报 already exists：别的线已经抢到，结束对话。

执行器能开对话就开；开不了，结束对话并回一句"<单元号> 已完成，下一个是 <单元号>"，由用户手动开。交接只靠分支和 tag，不依赖哪个执行器。

## 5. 契约要改时

线上单元停下，由用户决定。改：用户批准后在主目录改共享模块和 `docs/specs/` 对应小节，提交到主分支（带集成单元号和「硬线：」行），各线在自己分支上合并一次主分支。不改：单元按现有契约做，覆盖不到的部分在「决策与偏差」写一行，开后续单元。

## 6. 收尾阶段：集成单元

在主目录主分支上执行，验收方式固定 B。写入范围默认包括合并冲突涉及的文件、测试目录、测试配置和 docs。任务：

| 任务               | 做什么                                                                                                                                                                                                                                               |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T01 合并           | 按线号顺序 `git merge --no-ff gNN/Lk`，提交信息带集成单元号。合并前跑 `git diff --stat gNN/start gNN/Lk -- <hardline 路径>`：有改动又不是第 5 节批准或 spec 授权的，停下报告。`docs/backlog.md` 冲突不计数：取主分支版本，再改刚合并那几个单元的行。 |
| T02 全量测试       | 类型检查、lint、构建、各槽位测试、各端界面 e2e。                                                                                                                                                                                                     |
| T03 跨线组合       | 本组新增、跨线才走得通的路径写成一条 e2e；真实外部服务的冒烟测试经正式代码路径跑，不在测试里另拼请求。                                                                                                                                               |
| T04 用户能直接启动 | 按环境清单的授权把开发库迁移到最新；在主目录起各端，健康检查通过、能登录，然后停掉；在 plan「交接」写启动说明。                                                                                                                                      |
| T05 交付与归档     | 人工项登记「待人工验收」，用户确认后归档；其余按线、线内顺序归档。对账范围是 `git log gNN/start..gNN/Lk` 里带该单元号的提交，加上主分支上带该单元号的回修。                                                                                          |
| T06 清理与审查     | 起停脚本 `status` 为空，槽位和开发端口无监听，独占设备已释放；写进证据。独立审查只审本单元的改动；归档本单元。                                                                                                                                       |

## 7. 合并后出的问题

- 能定位到某个线上单元的，算它的回修：记进它 `plan.md` 的「回修」，提交写它的单元号。
- 定位不了的（几条线组合出的问题、测试设施、共享模块漏了），记进集成单元的「决策与偏差」，当场修的提交写集成单元号。
- 集成单元不替线上单元补证据：缺证据的回到那条线的分支补齐，再重新合并。

## 8. 收组

- 集成单元（或接力的线尾）归档前不要归档线上的对话：有的执行器归档对话时会删它的工作树。
- 归档后，用户归档本组全部线上对话，让执行器自己删工作树；再 `git worktree list` 与 `git worktree prune` 核对。注销后目录里可能剩被忽略的文件（依赖目录、env 副本），确认没有被跟踪的改动再删。分支和 tag 删不删由用户决定。
- `scripts/workflow.conf` 的 `active-units-max` 改回。
